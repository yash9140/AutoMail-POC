# Known Limitations

- **Maximized/full-screen Outlook only, for now.** Phase 2 enforces this window state (`app/outlook/launch.py::enforce_maximized()`) before readiness verification proceeds; restored-window and multi-resolution support are explicitly out of scope for this milestone, though nothing in the grounding architecture (fully dynamic, fresh-screenshot-driven, 0-1000 normalized coordinates) blocks adding it later.
- **Maximize enforcement has not been exercised against a real Outlook window.** All 19 Phase 2 tests mock `ctypes.windll.user32` — `IsZoomed`/`ShowWindow(SW_MAXIMIZE)`'s actual real-world behavior against the live Outlook window (timing of the OS's own resize animation, whether `MAXIMIZE_STABILIZE_WAIT_SECONDS` (1.0s) is actually enough on a real machine) is unverified until the first live run, which requires separate explicit approval.
- **Provider retry is single-attempt (`PROVIDER_RETRY_COUNT = 1`), not exponential backoff.** A second consecutive technical failure on the same call still classifies as `PROVIDER_ERROR` — appropriate for keeping a live run's total duration bounded and predictable, but means a Vision provider having a genuinely bad few seconds could still stop a run that a longer backoff might have ridden out.
- **Resolved (Phase 3): Phase 2 launch-result metrics now propagate into `FindOpenEmailSteps`' result** (`FindEmailResult`, a subclass of the historical `RND009CResult` — never edits `rnd/`). They still do NOT propagate one level further into `ReplyDraftSteps`' folded-in result — `app/outlook/draft.py::run_find_and_open_email()`'s copy loop iterates only the original `RND009CResult.model_fields`, so the new Phase 2/3 fields on `FindEmailResult` aren't among them. Deferred; not required by Phase 3's own scope.
- **Ambiguity resolution ("pick the latest") only succeeds when every candidate's `date_or_order` parses as an unambiguous ISO-8601 date/datetime with a unique maximum.** Free-text dates as Outlook actually displays them ("Yesterday," "Mon 9/1," "3:45 PM") will NOT resolve automatically — they fall through to `MULTIPLE_TARGET_EMAILS_FOUND`, a safe stop rather than a fabricated guess. Real-format date parsing is a candidate follow-up once a live run shows what Outlook's message list actually displays in the target environment.
- **The message-list scroll anchor/increment (`MESSAGE_LIST_SCROLL_ANCHOR_X/Y_FRACTION`, `MESSAGE_LIST_SCROLL_AMOUNT`) are untested against a real Outlook window** — all Phase 3 tests mock `pyautogui` in `app/automation/scrolling.py`; whether one scroll-wheel unit of `-6` moves a realistic number of rows, and whether the anchor fraction reliably lands inside the message-list pane across different Outlook window layouts, is unverified until a live run.
- **Gemini is the only empirically-proven provider.** OpenAI and Anthropic providers are implemented behind the same interface and mock-tested, but have never made a real API call (blocked on unfunded credits during RND-003B). Swapping providers is architecturally easy; it is not empirically validated.
- **Send grounding trades a hardcoded ground-truth check for a dynamic one.** The original RND-008 Send validation used a hardcoded pixel bounding box captured from one specific layout — exactly the kind of "resolution-specific coordinate" this POC's "no UI hardcoding" rule forbids. Phase 7 replaces it with the same dynamic bbox-validation pattern used everywhere else (self-consistency, bounds, shape/size plausibility, blocked-target-name list). This is a real, deliberate trade-off: structurally weaker than "verified against a known-good ground truth," accepted because Send remains protected by other unweakened controls (max-1-click hard limit, dual foreground checks, bounded non-reclicking post-send verification, two separate pre-run human approvals).
- **No live Send test has been run against this refactored code yet.** All of Phase 1's work (and subsequent phases through implementation) proceeds on mocked tests only. The first real end-to-end run — including any real Send — happens only after a separate, explicit approval.
- **Per-stage result models are still R&D-verbose.** `rnd/models/{outlook_launch,find_open_email,reply_draft}.py` (raw screenshot filenames, every intermediate attempt object, RND-numbered class names) are reused as-is by the moved step logic this phase, rather than replaced with a leaner final-POC schema — deferred to a later cleanup pass once every phase that touches them has landed.
- **Resolved (Phase 5): dynamic Reply-search is implemented** — bounded search + scroll (reusing Phase 4's `scroll_email_body()`), bbox grounding, exact-identity rejection of "Reply All"/"Forward"/etc. Send integration remains designed but not implemented — see `04_SCROLLING_AND_LONG_EMAIL.md`, Phase 7.
- **Reply grounding/scrolling is untested against a real Outlook window.** All Phase 5 tests mock `pyautogui`/the provider; whether the Reply control's actual on-screen position, size, and label text match what the prompt (`app/vision/prompts/reply_search_v1.txt`) assumes, and whether body-scrolling reliably brings a not-yet-visible Reply control into view, is unverified until a live run.
- **Reply-search semantic rejection relies entirely on Vision's own `control_identity` string being accurate.** The exact-match check (`"reply"` only, case-insensitive) is deterministic Python, but it can only be as good as what Vision reports — if Vision itself mislabels a non-Reply control as `control_identity: "Reply"`, the code-side check would not catch it (this is the same class of risk `validate_grounding()`'s bbox/confidence checks partially mitigate, but do not eliminate).
- **Differences between compact and full Outlook ribbon/toolbar layouts are unobserved.** No hardcoded layout-specific rules were added to compensate — if a live run surfaces a real layout variant Reply search doesn't handle well, that will inform a future prompt/validation refinement, not a hardcoded workaround.
- **Long-email accumulation's `requires_reply`/`sender_intent`/`requested_action` judgment comes entirely from the LAST section's holistic assessment**, not a dedicated final synthesis call — chosen to avoid an extra Vision call per read (each section prompt already receives the accumulated tail as context, so the last section's judgment is genuinely informed by everything read). This has not been validated against a real multi-section email; whether Gemini's holistic judgment stays reliable across many accumulated sections is unverified until a live run.
- **The email-body scroll anchor/increment (`EMAIL_BODY_SCROLL_ANCHOR_X/Y_FRACTION`, `EMAIL_BODY_SCROLL_AMOUNT`) are untested against a real Outlook reading pane** — same caveat as Phase 3's message-list scroll constants, unverified until a live run.
- **Overlap detection (`_strip_overlap()`) is a simple exact-prefix string match**, not fuzzy — if Vision's reported `overlap_text` doesn't match the new section's content byte-for-byte at the start (e.g. due to minor OCR-like transcription differences between calls), the overlap silently fails to strip and the duplicated text is kept rather than dropped. This is a deliberate conservative choice (never strip content that doesn't provably overlap) but means some duplication may survive in practice.
